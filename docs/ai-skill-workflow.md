# AI 协作与 Skill 固化

## 我是怎么在 AI 的帮助下完成这个项目的

这次适配并不是“把需求发给 AI，等它一次性吐出全部结果”，而是把 AI 放在几个真正能放大效率的位置上：

### 1. 在动手前先梳理问题

先用 AI 帮忙把任务拆开：

- 协议设计问题是什么
- 哪些能力应该放在核心仓库
- 哪些能力应该放在 Android 客户端
- 哪些内容适合做 UI，哪些应该继续留在 JSON

这一步最大的价值，是把“想法”变成可以落到代码结构里的任务列表。

### 2. 让 AI 帮忙映射到现有代码结构

真正高效的点，不是让 AI 脱离上下文乱写代码，而是让它先读仓库，再回答：

- `wangwang` 相关入口应该挂在哪
- 哪些文件最适合做最小改动
- Android 侧要不要做完整协议表单
- 怎样在不破坏上游结构的前提下把功能加进去

最后我们选择的是一条很克制的路线：

- 保留 JSON 导入和 JSON 编辑器
- 只对含 `wangwang` outbound 的本地配置显示额外入口
- 新增一个最小编辑页，只编辑四个核心字段

### 3. 用 AI 协助排障和补文档

在实现过程中，AI 更像一个持续在线的结对同事，适合做这些事：

- 检查变更范围有没有太大
- 帮忙审视路径是否符合上游结构
- 整理构建步骤、验收标准和发布材料
- 把零散操作记录收敛成以后还看得懂的文档

真正关键的判断仍然要靠你自己完成：

- 代码是不是符合仓库风格
- 实际构建有没有通过
- 配置是否真的能导入和连通
- 文档有没有泄漏真实环境信息

## 为什么要把经验固化成 skill

单次聊天很容易丢上下文，尤其是下面这些内容：

- 双仓联动关系
- Android 构建前置条件
- AAR 产物应该放哪
- 哪些字段适合做 UI，哪些不适合
- 发布前要清理哪些敏感信息

而 skill 的价值就在于把这些“每次都会重新想一遍”的经验固定下来。

## 一个好用的 skill 应该包含什么

以这次的 `sing-box-wangwang-android` 为例，一个实用 skill 至少应该写清楚：

- 仓库布局假设
- JDK / Android SDK / NDK / gomobile 前置条件
- 构建 `libbox` AAR 的标准命令
- Android APK 的构建命令
- 最小 UI 方案的边界
- 配置脱敏要求
- 最低验收清单

这样做的好处是：

- 下次继续迭代时，不用从零回忆
- 换一个 AI agent 也能快速接手
- 你的“个人经验”变成“团队可复用资产”

## 这次沉淀出的 workflow

这次项目里最值得保留的不是某一段代码，而是下面这条可重复 workflow：

1. 先在核心仓库实现并验证 `wangwang` 协议。
2. 构建包含 `wangwang` 的 Android `libbox` AAR。
3. 把 AAR 接入 `sing-box-for-android`。
4. 保持 JSON 导入为主路径，只补最小可用编辑器。
5. 用固定清单验证导入、编辑、连通和 APK 构建。
6. 最后再补 GitHub 文档和开源说明。

## 后续如何继续扩展

如果你后面还要继续维护，建议把 skill 再往前走一步：

- 为常用命令补一个统一脚本入口
- 把验收结果模板化
- 为开源发布补 release checklist
- 把核心仓库和 Android 仓库的关系写成统一首页说明

这样以后不论是你自己、合作者，还是另一个 AI agent，都会更容易稳定接手。
