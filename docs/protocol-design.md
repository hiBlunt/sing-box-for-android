# Wangwang 协议设计说明

## 背景

这个 Android 仓库对应的是一套成对维护的开源方案：

- 核心仓库负责在 `sing-box` 中实现 `wangwang` 协议
- 当前仓库负责把这套能力带到 Android 客户端

所以这里的协议说明重点不是重复所有底层实现细节，而是解释这套设计为什么存在、为什么值得做成 Android 可用版本，以及它的边界在哪里。

## 设计初衷

`wangwang` 的设计目标主要有四个：

1. 让连接首包尽量表现得更像普通 HTTP 请求，而不是典型的“完全随机密文首包”。
2. 保留真实业务载荷的机密性，用 AEAD 保护后续传输内容。
3. 对错误密码、畸形请求和主动探测，尽量通过 fallback 给出更自然的外部行为，而不是直接暴露代理服务特征。
4. 尽量复用 `sing-box` 原有的配置模型、路由能力、TUN 能力、libbox 构建链和 Android 客户端能力。

换句话说，`wangwang` 不是为了“重新发明一个代理框架”，而是为了验证一种更适合特定网络环境的协议形态，并尽快落到真实可用的工程路径里。

## 设计依据

### 1. 来自公开研究的启发

`wangwang` 的设计过程参考了关于 GFW 主动探测与流量识别的公开研究，尤其关注两个问题：

- 首包长得像什么，是否会影响进入进一步审查的概率
- 服务端在面对错误连接时怎样响应，是否会反向暴露自己是代理服务

这也是为什么 `wangwang` 会把“HTTP 风格首包”和“fallback 行为”当成协议设计里的重要部分。

### 2. 来自 Trojan 的工程经验

`wangwang` 在工程上明显借鉴了 `Trojan` 的一些成熟思路：

- 继续围绕密码鉴权和目标转发组织连接建立过程
- 继续重视错误请求、异常请求与 fallback 的行为一致性
- 继续保留与现有代理框架兼容的配置和接入方式

不同点在于，`wangwang` 并不依赖 TLS 包裹整个连接，而是把“首包伪装”和“后续加密”拆成两层来处理。

### 3. 来自 sing-box 现有生态的约束

选择在 `sing-box` 上扩展，而不是另写一套独立客户端，有很现实的原因：

- 已有成熟的路由、DNS、TUN 和多平台能力
- 已有 `libbox` 这条 Android 复用链
- 已有完整的配置模型和构建体系

这让 `wangwang` 能更快从“协议想法”进入“桌面可测、服务端可跑、Android 可用”的状态。

## 协议轮廓

按当前实现思路，一次典型的 `wangwang` 连接大致由三段组成：

1. HTTP 风格的明文首部
2. 每连接唯一的随机 salt
3. AEAD 加密后的真实代理载荷

可以把它理解为：

- 先用一个更自然的首包形态进入连接
- 再用对称加密保护真正的业务数据
- 服务端对异常连接走 fallback，而不是暴露明确错误

## 为什么 Android 端只做“最小编辑器”

Android 端的设计重点不是把所有 `wangwang` 字段都做成完整 GUI，而是优先解决“能导入、能运行、能改最常用字段”。

因此当前客户端只为本地配置中的 `wangwang` outbound 提供四个字段的图形化编辑：

- `server`
- `server_port`
- `password`
- `method`

这样做有几个实际好处：

- 改动小，便于持续同步上游 SFA
- 用户最常改的字段可以避免手输 JSON
- 高级配置仍保留在 JSON 里，不会因为 UI 不完整而丢字段
- 出问题时，仍然可以回退到 JSON 编辑器这个完整入口

## 优点

- 首包更接近普通 HTTP，形态上更自然
- 后续业务流量仍有 AEAD 加密保护
- 错误密码、畸形报文和探测连接可以走 fallback，减少显式暴露
- 能复用 `sing-box` 的路由、DNS、TUN、libbox 和 Android 构建链
- Android 端不需要大规模重写配置系统，只做最小必要适配

## 缺点与权衡

- 明文首部并不隐藏所有元信息，它优化的是首包形态，不是“绝对不可识别”
- 不依赖 TLS，也就失去了一部分借助成熟 TLS 生态伪装的能力
- fallback 机制意味着部署复杂度会高于最简单的单端口代理
- 这是研究型扩展，不应包装成经过长期公开审计的标准协议
- 继续跟进上游时，需要同时维护核心实现、libbox 构建和 Android 适配

## 适用场景

更适合：

- 协议研究和工程验证
- 需要多平台一致接入路径的实验性项目
- 已经在用 `sing-box`，希望最小代价把协议扩展带到 Android

不适合：

- 期待“一种协议解决所有对抗问题”的表述
- 需要完整 GUI 覆盖所有高级配置的最终产品
- 不愿意承担跟随上游同步维护成本的场景

## 使用建议

- 把当前仓库和 `wangwang` 核心仓库一起开源说明，不要割裂介绍。
- 在公开文档里使用占位 IP、端口和密码，不要泄漏真实基础设施。
- 把 Android 端定位成“最小可用的官方样式客户端 fork”，而不是完全独立的新产品。
- 对外说明时强调这是研究型工程实现，避免过度承诺。
